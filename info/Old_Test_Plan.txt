## 1. Goals and approach

The brief asks how I think about risk, not for coverage. So:

1. Rank areas by business damage if they fail. Test the top of the list deeply and say what I skipped.
2. Prove each bug with a **failing automated test** that asserts the *correct* behaviour.
3. Use the cheapest layer that can prove the claim. Vitest with mocks for authorization logic, Vitest against real Postgres for query-scoping claims, and exactly one Playwright journey.

### Risk ranking

| # | Area | Why it ranks here |
|---|------|-------------------|
| 1 | Access control and the publish gate | Draft catalogues hold confidential negotiated pricing (the seed has "Northstar pricing — do not share"). A leak or an unauthorised publish is irreversible. |
| 2 | Enquiry intake (`POST /api/enquiries`) | This is the revenue path. It is public, unauthenticated, and writes price snapshots that sales will honour. |
| 3 | Catalogue lifecycle: draft / published / expired | Wrong status means stale prices are honoured, or live catalogues look dead to admins. |
| 4 | Spreadsheet import mapping | Bulk operation. A wrong column mapping silently corrupts hundreds of prices or stock counts. |
| 5 | Price and discount maths | Small code, but shown to every buyer. |
| 6 | UI components, analytics, notifications, S3 presign, newsletter, rich text, badges | Low blast radius or covered by third parties. Mostly out of scope (§8). |

### Logic bugs

| ID | Defect | Evidence | Severity |
|----|--------|----------|----------|
| BUG-06 | **`effectiveStatus` is inverted.** The test is `expiresAt > new Date()`, so a published catalogue with a *future* expiry shows "expired" and an *already expired* one shows "published". | **[RAN]** published + expires in 30 days → `expired`; published + expired 30 days ago → `published`. | **High** (admin dashboard, detail page and global search all use it) |
| BUG-07 | **`autoMap` mis-maps common headers** through substring matching in a fixed order. Run on `["List Price","Offer Price","Min Qty","Available Quantity"]`: `List Price → offerPrice` (should be MRP), `Offer Price → attribute` (price dropped), `Min Qty → quantity` (should be MOQ), `Available Quantity → attribute` (stock dropped). | **[RAN]** | **High** (silent bad import) |
| BUG-08 | **Enquiry reference collides.** `ENQ-${Date.now().toString().slice(-7)}` repeats every ~2.8 hours and for any two enquiries in the same millisecond. `reference` is `@unique`, so the second insert fails with a generic 500 and the buyer's lead is lost. | **[READ]** | **High** (lost leads, rare but silent) |
| BUG-09 | **UI and API disagree on quantity for low-stock products.** The dialog allows `max(moq, stock)`, so it sends `moq` even when `stock < moq`. The API requires `moq ≤ qty ≤ stock` and answers 400. The buyer sees an "Enquire" button that can never succeed. | **[READ]** `contact-supplier-dialog.tsx` vs `api/enquiries/route.ts` | Medium |
| BUG-10 | **`validUntil` accepts impossible dates.** The regex is only `\d{4}-\d{2}-\d{2}`. `2026-02-31` silently becomes **3 Mar 2026**. `2026-13-01` becomes `Invalid Date`, which makes Prisma throw and returns a generic 500 instead of a 400. | **[RAN]** (date part) / **[READ]** (500 path) | Medium |
| BUG-11 | **Live catalogue prices can be blanked.** `updateProductPrices` accepts `mrp:null, offerPrice:null` for products in a published catalogue. This bypasses the "incomplete products can't be live" rule enforced elsewhere. | **[READ]** `products/actions.ts` | Medium |
| BUG-12 | **Archived products can be added to catalogues via the API.** Only the picker UI hides them; `addListingsSchema` and `createCatalogueWithProducts` never check `archivedAt`. | **[READ]** | Medium |
| BUG-13 | `setCatalogueStatus("published")` overwrites `publishedAt` even when the catalogue is already published. The PATCH route only sets it on a transition. | **[READ]** | Low |

### Data-quality observations (document; low priority)

- `discountPercent` returns **−50** when `offerPrice > mrp` **[RAN]**. The UI hides it (`discount > 0`), but nothing validates offer ≤ MRP anywhere (form, import, bulk price update).
- `parseNumber("0x10")` returns 16 and `parseNumber("1e3")` returns 1000 **[RAN]**. Currency symbols are stripped anywhere in the string.
- The server import action re-validates row shape but not duplicate SKUs within a sheet. A duplicate produces the misleading "Another import added…" message. `importJob.errorCount` is always 0.
- `money()` rounds to whole rupees, so ₹2,499.50 displays as ₹2,500 while the lead detail page shows 2,499.5.
- `completeProductsForSale` / duplicate-product logic is repeated three times (the incomplete-product query and mapping).

### 4.2 Integration tests against real Postgres

These prove query-scoping claims that a mock cannot prove:

- **BUG-04** — create catalogues A and B with a listing in B. Call the PATCH/DELETE handler with A's id and B's listing id. Expect 404 and B's listing unchanged.
- **BUG-05** — create draft, expired and published catalogues. POST an enquiry to each. Only the live one may return 201.
- **BUG-08** — freeze `Date.now`, create two enquiries, and check the second is not a 500. Then two calls `10_000_000` ms apart must produce different references.
- **Enquiry snapshot** — after an enquiry, change the product price. The lead item still shows the original `unitPrice`, name, SKU and brand. A `priceOnRequest` product snapshots `unitPrice = null`.
- **Listing delete** — deleting a listing keeps the enquiry item (`SetNull`) and its snapshot.
- **Archive** — `archiveProducts` removes listings and sets `archivedAt`. Import skips archived SKUs. Restore leaves the product unlisted.
- **Stock derivation** — a product with city rows has `quantity == sum(rows)`. `updateProduct` and import must not overwrite it.
- **Import transaction** — a failing row rolls back the whole batch ("Nothing was added").

## 6. Task 4 — One end-to-end journey (Playwright)

**Journey:** open the published catalogue → browse and search → open a product → submit an enquiry → find it in Admin Leads Inbox.

## 9. Handling failing-by-design bug tests

The brief wants a test that **fails because of the bug**. A red suite is useless as a daily signal, so:

- Name each one `BUG-NN: <expected correct behaviour>` and keep them in `tests/bugs/`.
- Assert the **correct** behaviour. Do not use `it.fails` or assert the broken behaviour, or the test stops proving anything when the bug is fixed.
- `npm test` runs everything and shows the BUG tests red. Add `npm run test:regression` (everything except `tests/bugs/`) as the green gate. In the CI bonus, regression blocks merges and `tests/bugs/` reports as a non-blocking warning until the fixes land.
- `FINDINGS.md` lists the exact test file and test name for each bug.
